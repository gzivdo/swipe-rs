# swipe-rs

Чисто-DSP реализация **SWIPE'** / **SWIPE** — оценщика основной частоты
на Rust. Без нейросетей, без файлов весов, без обучения — только FFT,
матрица ядер и математика из двух опубликованных статей.

Работает с **моно-аудио 48 кГц `f32`**. Удобен для потоковой обработки:
подаёте чанки любого размера и получаете ноль или больше кадров
`(время, Гц, уверенность)` за вызов.

```rust
use swipe_rs::Swipe;

fn main() -> Result<(), swipe_rs::Error> {
    let mut swipe = Swipe::new()?;
    // 48 кГц моно f32, чанк любого размера:
    let frames = swipe.process(&audio_chunk)?;
    for f in frames {
        if f.confidence > 0.3 {
            println!("{:6.3} s  {:6.1} Hz  conf={:.2}",
                     f.time_s, f.pitch_hz, f.confidence);
        }
    }
    Ok(())
}
```

Добавить в `Cargo.toml`:
```toml
[dependencies]
swipe-rs = "0.2"
```

### API без аллокаций для realtime

Если вы обрабатываете аудио в плотном цикле и не хотите свежий `Vec`
при каждом вызове, используйте [`Swipe::process_into`] — он дописывает
в буфер, которым владеет вызывающий код:

```rust
use swipe_rs::{Swipe, PitchFrame};

let mut swipe = Swipe::new()?;
let mut frames: Vec<PitchFrame> = Vec::with_capacity(64);

loop {
    let chunk = read_audio_chunk();
    frames.clear();                          // опционально — см. документацию
    swipe.process_into(&chunk, &mut frames)?;
    for f in &frames { /* … */ }
}
```

После первой секунды аудио `Vec` достигнет установившейся ёмкости и
больше никогда не будет перевыделяться. Функционально эквивалентно
`process()`; выбирайте по вкусу.

## Что такое SWIPE

Оба алгоритма оценивают основную частоту $f_0$ оконного аудио-кадра так:

1. **Строится банк спектральных ядер** — по одному на каждого кандидата
   высоты тона. Каждое ядро похоже на квадратный корень амплитудного
   спектра пилообразного сигнала, прошедшего окно Ханна на этой высоте:
   положительные косинусные лепестки в позициях гармоник, отрицательные
   косинусные впадины между ними.

2. **Каждый кандидат оценивается** как cosine-similarity-подобное
   скалярное произведение его ядра и (квадратного корня)
   амплитудного спектра входного кадра.

3. **Выбирается argmax** в качестве оценки $f_0$.

**SWIPE'** оставляет лепестки только на $f_c$ и на *простых-гармонических*
кратных ($2f_c, 3f_c, 5f_c, 7f_c, \ldots$), что подавляет суб-октавные
ошибки, которые обычный SWIPE даёт на пилах и подобных богато-гармонических
сигналах. Этот крейт реализует SWIPE'.

Статья Marttila & Reiss (2025) расширяет SWIPE Камачо двумя
ключевыми приёмами:

- **Окна нескольких разрешений** — амплитудный спектр считается на
  нескольких размерах FFT (степени двойки от 1024 до `max_window`),
  и для каждого кандидата два соседних окна линейно смешиваются в
  пространстве $\log_2(W)$, чтобы аппроксимировать идеальное
  $W_c = 8 f_s / f_c$. Это разделяет охват низких частот (длинные окна)
  и точность на высоких (короткие окна).

- **Семплирование по mel-оси** — ядра и спектры семплируются на
  1024-точечной mel-оси вместо линейных бинов. Это концентрирует
  разрешение там, где оно важно (низкие гармоники), и резко улучшает
  точность на речи и музыке — сравнимо с обученными моделями вроде
  CREPE на стандартных бенчмарках (96.4% RPA на MIR-1K, Таблица 4 статьи).

В итоге получаем детектор высоты тона, который сравним с CREPE/pyin на
монофоническом аудио без какой-либо нейросети — только FFT, умножение
матриц и argmax.

## Как он сравнивается?

Монофоническое определение высоты тона — переполненная ниша.
Заголовочные числа из опубликованных оценок и наших измерений на одном
и том же вокальном стеме:

| алгоритм | тип | файл весов | задержка @ 48k | RPA на MIR-1K | лицензия | примечания |
|---|---|---|---|---|---|---|
| **swipe-rs** (этот) | чистый DSP | **нет** | 85 / 170 / 340 мс* | **96.2 / 96.4 / 96.4 %** ¹ | Apache-2.0 | без обучения, без файла модели, без GPU |
| pyin | чистый DSP | нет | ~333 мс (хоп 333 мс) | 84-87 % ² | GPL-3 (Rust-крейт) / ISC (librosa) | очень консервативное определение голоса — высокая точность, низкий recall |
| Praat AC | чистый DSP | нет | ~20 мс | 87-89 % ² | GPL-3 | классическая автокорреляция, быстро, но склонна к октавным ошибкам |
| **CREPE** (full) | CNN | 85 МБ | ~50 мс | 95.4 % ³ | MIT | дружелюбен к ONNX, мультиязычный, общий чемпион |
| CREPE (tiny) | CNN | 1.9 МБ | ~50 мс | 92-93 % ³ | MIT | вариант small-and-fast |
| **SwiftF0** | малая CNN | 400 КБ | ~70 мс | n/a (под вокал) | MIT | самая маленькая нейромодель, которая работает |
| PESTO | tiny CNN | 17 МБ | ~50 мс | 94 % (по статье) | MIT | гибрид CQT + энкодер на 130k параметров |
| **RMVPE** | CNN | 362 МБ | ~50 мс | n/a (только вокал) | Apache-2.0 | обучен на пении, устойчив к полифонии — извлекает вокальный pitch сквозь аккомпанемент |
| Aubio yin/fcomb | DSP | нет | ~10 мс | 75-85 % ² | GPL-3 | для embedded; устарел |

*Задержка = столько сэмплов из самого большого окна нужно, чтобы выдать
последний кадр. Realtime-пресет (4096) → 85 мс; Balanced (8192, по
умолчанию) → 170 мс; Full range (16384) → 340 мс.

¹ Marttila & Reiss, ISMIR 2025, Таблица 4 — MIR-1K, ±50¢ RPA.
² Различные статьи; диапазоны отражают разные условия оценки.
³ Kim, Salamon, Li, Bello, "CREPE: A convolutional representation for
   pitch estimation," ICASSP 2018.

### Что это означает на практике

Мы прогнали все шесть оценщиков контура (pyin, SwiftF0, CREPE,
SwipeF0 = этот крейт, RMVPE, PESTO) на реальных вокальных записях в
рамках офлайн-пайплайна извлечения pitch. Сводные выводы:

- **Чисто-DSP SWIPE сравним с маленькими нейросетями на вокале**, если
  вы можете позволить себе окно 170 мс. В пределах пары процентов от
  CREPE по RPA — и единственный в таблице, кто не везёт ни байта
  предобученных весов.
- **Доля октавных ошибок на гармонически-богатых сигналах (поп-вокал,
  медь, пилы): SWIPE ≈ 13-15 %** озвученных кадров, против ≤ 5 % у
  pyin / CREPE / SwiftF0 / RMVPE. Ядро на простых гармониках подавляет
  суб-октавные ошибки, но не убирает полностью октаву вверх. *Если* у
  вас есть второй источник pitch (любой из остальных), запуск SWIPE
  параллельно и приведение swipe→ближайшему-соседу по октаве даёт
  лучшее из двух миров.
- **Для пения RMVPE сложно побить** — но файл модели в 362 МБ делает
  его менее привлекательным для embedded / распространяемых сборок.
  SwipeF0-rs и pyin — лёгкие DSP-альтернативы.
- **Задержка против точности у SWIPE — монотонна.** Realtime-пресет
  (4096) теряет ~0.2 п.п. RPA на бенчмарке статьи против Balanced;
  ниже 2048 начинаете терять реально.
- **Голосовое решение pyin — золото**, если ложные срабатывания дороги
  (например, лучше малая доля озвученных кадров с 95% precision, чем
  большая с 80%). SWIPE и CREPE оба более охотные.

### Когда выбирать swipe-rs

- Не хотите везти модель на 300+ МБ.
- В вашей сборочной среде нет ONNX / PyTorch / TFLite.
- Нужен детерминированный, аудируемый алгоритм — никаких непрозрачных весов.
- Целитесь в embedded / WASM, где добавить 1 МБ к бинарю — много.
- Не нужна устойчивость к полифонии (вокал-сквозь-микс → берите RMVPE).

### Когда выбирать что-то другое

- **Максимальная точность на вокале без ограничений по размеру** → RMVPE.
- **Самый быстрый realtime на обычном CPU с отличной точностью** →
  SwiftF0 (400 КБ, ~70 мс задержки).
- **Хотите академический эталон по RPA на разных инструментах** →
  CREPE (full).
- **Уже линкуете librosa или torchaudio** → берите их `pyin` (вы и так
  платите за зависимость, а pyin уже обкатан).

## Конфигурация

| пресет | `max_window` | задержка | минимальная высота | RPA на MIR-1K |
|---|---|---|---|---|
| Realtime | 4096 | ~85 мс | ~94 Гц | 96.2% |
| Balanced (по умолчанию) | 8192 | ~170 мс | ~47 Гц | 96.4% |
| Full range | 16384 | ~340 мс | ~23 Гц | 96.4% |

```rust
use swipe_rs::Swipe;
let realtime  = Swipe::with_max_window(4096)?;
let balanced  = Swipe::new()?;                  // по умолчанию
let full_rng  = Swipe::with_max_window(16384)?;
```

Узкое место — FFT размера `max_window` на каждый выдаваемый кадр —
хоп ~10 мс, так что Realtime-инстанс работает >100× быстрее реального
времени на одном современном ядре CPU.

## Определение голоса (voicing)

Возвращаемая `confidence` — это пиковая оценка SWIPE в `[0, 1]`. На
реальном вокале она держится около `0.3..0.6` для чётко озвученных
кадров и `0.05..0.2` для безголосых/тишины. Стандартный порог:
`confidence ≥ 0.3`.

В статье точность классификации voiced/unvoiced даётся без фиксированного
порога — берётся просто глобальный argmax. Для практического realtime
рекомендуется порог либо небольшой пост-фильтр (медианный) по уверенности.

## Тесты

```bash
cargo test
```

- Чистый синус на 220, 440, 880, 1760 Гц на пресете Balanced по
  умолчанию → оценка в пределах 50 центов (планка `mir_eval` Raw Pitch
  Accuracy).
- Пила на тех же основных частотах → тот же допуск, валидирует веса
  ядра простых гармоник.
- Синус 100 Гц на пресете Full range (`max_window=16384`) → в пределах
  50 центов (Balanced лишён низкочастотного окна).
- Потоковый чанкованный вход → идентичные кадры пакетной обработке.

Суб-сентовая точность случается на чистом синтетическом входе, но не
гарантирована на краях сетки кандидатов (36 бинов/октаву ≈ 33 цента
на бин; параболическое уточнение сужает это дальше). Для практического
pitch-трекинга на реальном аудио считайте алгоритм точным до ±50 центов.

## Дорожная карта

- **Поддержка `no_std`** — сейчас заблокирована апстримом. `realfft`
  построен на `rustfft`, который зависит от `Vec`/`Box` из `std` и не
  имеет конфигурации `#![no_std]`. Когда `rustfft` обзаведётся
  `no_std + alloc`, swipe-rs последует с флагом
  `default-features = ["std"]` для embedded / WASM-no-stdlib таргетов.
  (Никаких `Send`/`Sync`, никакой многопоточности, никакого I/O —
  сам алгоритм чисто числовой.)
- **In-place выход для `no_alloc`** — после прихода no_std дать
  `process_into_slice(audio, out_slice) -> Result<usize, _>`, который
  заполняет фиксированный `[MaybeUninit<PitchFrame>; N]` для настоящей
  zero-allocation работы. Текущий `process_into(&mut Vec<_>)` — это
  zero-allocation *амортизированно*; slice-вариант будет
  zero-allocation всегда.
- **Более плотная сетка pitch** — текущая сетка 36 бинов/октаву плюс
  параболическое уточнение даёт ~10-сентовую практическую точность на
  синтетическом входе. Более плотная сетка (или другое уточнение)
  помогло бы для приложений ретюнинга. Не на критическом пути статьи.
